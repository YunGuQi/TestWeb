# 02_测试设计 - 融入当前框架版 (test-platform 统一大盘篇)

当用户在【阶段 2：测试设计】中选择了**“融入当前框架版 (test-platform 统一大盘)”**时，AI 需要指导或协助完成从策划案至大盘集成的端到端研发。

---

## 1. 架构目标与前置原则

1. **直接接入现有工作区**：在 `design/test-platform/` 下进行整体开发，不要创建任何新的 Next.js 项目。
2. **多测试租户隔离**：数据库实体表 (`Question`, `Option`, `ResultConfig`, `TestRecord`) 都含有 **`testId`** 字段。每一个测试必须有一个唯一的 URL Slug（例如 `emotional-friction`、`city-personality`、`career-test` 等）。
3. **数据和管理统一**：所有接口和管理员操作通过 `testId` 过滤，使 `/admin` 面板切换不同测试时数据互不干涉。

---

## 2. 研发 SOP 步骤

### 第一步：创建测试前端路由与视图 (`app/<new-test>/page.tsx`)
- 在 `design/test-platform/app/<新测试标识>/` 创建页面主入口 `page.tsx`。
- 页面应包含完整的状态切换：
  - **LandingView** (首页封面、标题、触发按钮)
  - **QuizView** (题库展示、进度条、选项点击)
  - **ResultView / ReceiptView** (最终测算结果或收据卡片呈现)
  - **HistoryDrawer** (查看当前设备的过往测算记录)
- **要求**：严格使用对标策划案中的视觉风格（如 Brutalist 粗野主义或卡片式布局），保留所有交互动效（可以使用 GSAP / CSS micro-animations）。

### 第二步：数据库表与初始数据植入 (`Prisma Seed` / API)
- **不可建新表**，复用 `prisma/schema.prisma` 中的统一表定义。
- **数据库连接与数据上传**：测试大盘的 Prisma Postgres 云端数据库环境**已经准备就绪**（环境变量已配置好）。如果遇到连接失败，优先排查网络连通性。在开发新测试时，无需再询问用户是否需要部署数据库，而是应当直接在后续研发步骤中，**自动执行**结构推送和数据播种（如 `npx prisma db push` / `npx prisma db seed`）将数据上传至云端数据库。
- 准备新测试的题库与结论卡数据：
  1. 可通过修改 `prisma/seed.ts` 增加对应 `testId` 的题目与卡片并运行 `npx prisma db seed`。
  2. 也可以编写临时迁移脚本（如 `scripts/seed-<new-test>.ts`）往 SQLite/PostgreSQL 写入数据。
- 无论题目选项携带何种计重数据，都在 `Option.scores` 中以标准 JSON 字符串形式持久化（例如 `{"typeA": 2, "typeB": -1}`）。

### 第三步：对接后端算分与安全接口
1. **获取题目**：
   - 调用 `GET /api/questions?testId=<新测试标识>`。
   - 验证后端传来的题目列表**未携带 `scores` 字段**，确保纯净安全。
2. **提交测算与算分 (`POST /api/submit`)**：
   - 前端传参：`{ deviceId, testId: "<新测试标识>", answers: { [questionId]: optionId } }`。
   - 若测试使用标准积分加权打分，则复用通用 `/api/submit` 算分逻辑；若有独特的维度坐标模型，可在 `/api/<新测试标识>/submit` 下新建定制化后端服务，将算分结果写回 `TestRecord`。
3. **云端收据历史 (`GET /api/history`)**：
   - 保证历史页面能根据 `deviceId` 和 `testId` 从后台完整加载所有流水记录。

### 第四步：注册到 `/admin` 后台面板
- 将该测试的 `testId` 注册到后台顶部的测试切换菜单中，便于运营人员统一维护题目、结论及查看提交数据概况。

## 3. 前端用户区（C端）核心功能与架构

> 📎 **页面功能定位**已在《策划篇》的「5. 产品页面规划」中完整描述，此处仅记录技术实现规范，不重复产品功能定义。

1. **全局视觉风格（动态定制情境 UI）**
   - **核心基调**：开发前必须首先阅读《产品方案》中设定的“统一包装隐喻”（如处方单、机票、说明书、结账小票等），并基于该隐喻为其定制一套高度契合的专属视觉风格。
   - **通用 CSS 规范制定**：
     - **色彩与背景**：拒绝默认大白墙，必须设计符合隐喻的背景特征（如医院处方单的暗纹/网格，机票的打孔纹理等）。
     - **字体排印**：必须配置贴合主题的字体组合（如医疗风的无衬线严谨字体，票据风的 monospace 等宽字体）。
     - **UI 组件重构**：所有按钮、卡片、输入框必须重写 CSS 样式，彻底剥离普通的圆角矩形，加入物理实体隐喻。
   - **核心物料设计**：首页的入口界面、答题过程的过渡动画、以及结果页的最终海报卡片，必须含有该隐喻对应的独特视觉元素（如：机票的条形码与登机口，处方单的医生印章，小票的波浪撕边等），确保极强的沉浸感和分享欲。

2. **`/` 首页 & `/explore` 矩阵页**
   - 首页次级按钮区使用 **Flex 并排布局**，`[查看历史档案]` 条件显示（读取 `localStorage["quiz_history"]`），`[探索更多测评]` 常驻。
   - `/explore` 卡片数据在 `explore/page.tsx` 的 `TESTS` 常量数组中维护，入场动画使用 Framer Motion `staggerChildren`。

3. **`/test` 测试答题页**
   - 选完后 300ms 自动跳转：`setTimeout(nextQuestion, 300)`；最后一题不自动跳转，由用户手动触发 `handleSubmit`。
   - `[← 上一题]` 使用 `AnimatePresence` 控制入场，仅在 `currentIndex > 0` 时渲染。

4. **`/result/[id]` 测试结果页（核心变现区）**
   - 🚨 **核心架构铁律**：结果页的所有前端排版、视觉交互、长图截取以及【订单验证解锁遮罩】，**必须严格无条件遵照 `02_测试设计.md` 中的要求实现（强制采用单页瀑布流架构与订单拦截）**。本研发篇不再赘述重复的 UI 规范。

5. **全局强制交互与排版规范（必须无条件遵守）**
   > 注意：以下提到的“人数”、“按钮文案”等具体用词，必须结合当前测试的具体风格（如医疗风、账单风）进行文案包装（例如账单风格就是“当前排队结账人数：128,555 人”）。
   - **【首页规范】**：
     - 首页必须显示测试介绍（文案需说明该测试能给用户带来什么，测试了哪些维度）。
     - 首页参与测试的人数必须紧贴放在**[开始测试]主按钮的正下方**，并且随机生成的人数基数不要那么多（追求真实感）。
     - 首页必须固定包含通往「其他测试」和「历史结果（历史消费单）」的入口。
   - **【答题页规范】**：
     - 左上角永远固定为“首页”入口，点击后可以直接返回首页。
     - 除了第一题之外，其他题目的答案下方永远要有「返回上一题（撤回）」的按钮。
     - 最后一题**必须在用户点击（选中）某个选项后，才显现明确的提交按钮**（如“打印账单”、“查看结果”等），点击该按钮后才进行跳转。
   - **【结果页规范】**：
     - 结果页最上方，必须固定显示“你是第 XXX 个完成测试的人”（配合主题文案包装）。
     - 必须在单页内完整展示所有的**深度解析维度**（必须包含 3 个以上的子维度，如：核心成因诊断、图表联动分析、破局建议等）。长图生成（截图）功能也随之调整为截取包含所有解析内容的完整单页。
     - 页面最下方，必须固定放置「重新测试」和「查看更多测试」的按钮。

### 交互与细节体验强制规范

在进行具体测试的开发时，必须遵守以下 6 条强体验规范：
1. **答题页选项印章常驻**：答案被点击后显示的“盖章”或选中动效，不要在短暂 Timeout 后清除，必须**常驻保留**在当前被点击的选项上，除非用户切换了选项。
2. **历史记录模块**：测试完成后必须有历史结果的存档功能。不仅要在后端记录，前端同时也需强制将结果摘要存入 `localStorage`（防止数据库宕机时无记录）。并在**首页**提供「查看历史档案」的明确弹窗或入口。
3. **私域激活码拦截**：所有测试的【结果页核心解析区】和【保存图片/账单】功能，默认必须被**模糊遮罩**覆盖。用户必须通过弹出的验证框输入从小红书引流获取的**激活码（验证码）**，通过 `/api/verify` 接口校验后，方可解锁全部解析文本并允许点击保存长图。
4. **首页在线人数**：首页展示的“已有 XX 人解密”等氛围数据，基数不宜过分夸张，随机范围建议控制在 `0-100` 之间。
5. **探索大厅引流**：在首页及结果页底部的明显位置，必须提供“探索其他测试”的直接入口，且必须统一超链接回系统大厅（`href="/"` 或 `/design/common/lobby.html`）。
6. **维度条防同质化**：结果页中若有雷达图或各个维度的条形比例展示，数值必须精确到**小数点后两位**，并利用 `Math.random()` 产生微小扰动避免所有人的截图数据完全一样。维度条的进度颜色需使用**双拼渐变色**（从左到右：左边深色，右边浅色，如 `bg-gradient-to-r from-[深色] to-[浅色]`）。
7. **运营大盘（/ops-dashboard）兼容与专属卡密前缀**：在上线或新增测试时，必须将该测试添加到后台运营大盘（`/ops-dashboard`）顶部空间导航栏（如 `AdminNav.tsx`）的工作区下拉菜单 `TESTS` 列表中，确保运营管理员可随时在大盘后台切换至该项目，进行卡密（激活码）的独立生成/管理/导出，以及对应题目与结果海报的统计和查阅。同时，**必须为每个测试在后台生成卡密接口（如 `/api/admin/generate`）中配置其专属的卡密前缀（如情绪内耗为 `EMO-`，城市匹配为 `CITY-`，命定恋人为 `DESTINY-`），禁止所有项目统一混用 `CODE-` 前缀**。
8. **数据库优先（DB-First）与本地全权常数兜底（Local Fallback）双线高可用**：每一个接入当前框架的测评项目，必须分别准备云端数据库表（`Question`、`Option`、`ResultConfig`，通过 `testId` 分离）与完整的本地静态数据文件（如 `lib/<testId>-data.ts` 包含题库与匹配结果）。任何题库查询 API（如 `/api/questions`、`/api/city/questions`）和答题算分 API（如 `/api/submit`、`/api/city/submit-test`），必须采取**“优先通过数据库动态查询；当遇到断网、云端超时、数据库异常或查询结果为空时，自动向本地常数题库和结果库降级兜底”**的机制，确保系统无论是生产在线运维、运营改动，还是本地断网调试，用户均能够 100% 完成从答题、分数判定到精美小票打印渲染的整个交互流程，永不白屏报错。
