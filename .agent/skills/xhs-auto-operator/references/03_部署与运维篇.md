## 5. Deployment SOP (部署标准操作流程)

### Step 5.1: Standard Release Flow (代码变更后的标准发布与特权脱壳流程)

> [!IMPORTANT]
> **【防泄密与安全脱壳铁律】**：因宿主机部署了透明加解密系统 (DLP/TSD)，直接使用系统压缩或非特权脚本打包会导致 `.css`/`.js` 文件被二进制加密，部署到宝塔后导致白屏或样式全崩！必须严格遵循以下流水线（详见 [05_防泄密与安全脱壳规范](05_防泄密与安全脱壳规范.md)）。

```bash
# 第一步：提交代码（在本地 test-platform 目录）
git add <修改的文件>
git commit -m "feat/fix: 描述变更内容"
git push origin main          # → 自动触发 Vercel 构建部署

# 第二步：特权脱壳一键打包（⚠️极其关键，一行搞定！）
npm run pack                  # 聚合流水线：自动生成内联CSS ➔ Webpack全量构建 ➔ Node特权脱壳生成 deploy.zip

# 第三步：宝塔手动上传与部署
# 1. 登录宝塔面板，进入项目根目录：/www/wwwroot/（如 test.mutong-xhs.top）
# 2. ⚠️ 极其关键：将 deploy.zip 上传至项目根目录，右键解压覆盖
# 3. 执行 pm2 restart all (或在宝塔 Node 项目管理器中重启服务)
```

### Step 5.2: ENV Only Update (仅更新 .env 配置)

# 路径：/www/wwwroot/.env

## 9. Local Fallback Troubleshooting (数据库双线兜底避坑说明)

在 [02_测试设计_4_全栈研发大盘篇.md](02_测试设计_4_全栈研发大盘篇.md) 中提到的“Local Fallback”双线兜底机制，**绝对不是指在 MySQL 断连时去读写本地的 `dev.db` (SQLite) 文件**。

1. **Prisma 技术限制**：Prisma 引擎在构建时就会根据 `provider = "mysql"` 锁死数据库驱动。如果线上是 MySQL 环境，系统根本无法在运行时动态切换去读取 SQLite 的 `.db` 文件。
2. **正确的高可用兜底实现**：
   - 兜底数据应提取为本地的 `.ts` 或 `.json` 常量文件（例如 `lib/xxx-data.ts`）。
   - **读取降级**：当检测到数据库查询失败时，代码直接返回该常量数据给前端展示，以防白屏。
   - **写入降级限制**：对于写入操作（如下单测算），在 DB 宕机时只能给出友好提示或放入消息队列排队，**绝对不要尝试把新增订单写入临时的本地 `.db`，否则会导致极难修复的数据脑裂（Split-Brain）灾难**。

## 10. Data Import SOP (业务数据更新与导入)

由于平台已全量接入 Baota MySQL 且开放了外网直连（本地 `.env` 的 `DATABASE_URL` 已经直接指向了宝塔的公网 IP `114.132.183.186`），因此后续任何关于测试题库、结果配置等**“业务数据”的更新，绝不需要再像以前那样把数据库文件手动打包上传到宝塔了！**

**标准的数据注入流程：**

1. **准备数据导入脚本**：在本地项目中准备好需要入库的脚本（例如已有的 `do_import.js` 或 `scripts/update_city.py`）。
2. **确认环境变量**：确保本地开发机上的 `.env` 里的 `DATABASE_URL` 指向的是宝塔线上 MySQL（切勿连错本地库）。
3. **本地一键直连写入**：
   - 直接在您**本地电脑**的终端执行脚本，例如：`node do_import.js` 或 `uv run python scripts/update_city.py`。
   - 脚本会通过网络直连宝塔 MySQL，将新配置的题库数据实时写入线上。
4. **即刻生效**：纯业务数据入库时，不需要执行打包，不需要操作宝塔，更不需要重启 PM2，写入成功后线上环境立即生效。
