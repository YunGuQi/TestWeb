# 04_跨平台构建与部署避坑指南

本篇详细记录在 Windows 本地编译、打包并部署至 Linux 宝塔服务器 (1核1G低配环境) 时遇到的核心跨平台构建与运行 Bug，以及对应的标准解决方案。

---

## 1. Turbopack Alias Bug (Next.js 15/16 默认 Turbopack 编译导致哈希别名 Bug)

### 1.1 Symptoms & Logs (现象与日志)
在宝塔 Linux 服务器部署完成后，访问 API 接口时出现 `500 Internal Server Error`。PM2 运行日志中抛出如下错误：
```
Failed to load external module @prisma/client-2c3a283f134fdcb6: Error: Cannot find module '@prisma/client-2c3a283f134fdcb6'
```

### 1.2 Root Cause Analysis (根源剖析)
- 从 Next.js 15/16 开始，**Turbopack 成为开发与构建的默认编译器**。
- 在 Windows 本地执行 `next build` 时，Turbopack 在解析外部依赖（如 Prisma）时，由于路径环境等差异，会计算出一个包含哈希码的虚拟路径别名（如 `@prisma/client-2c3a283f...`）并硬编码进 `.next` 的服务区模块中。
- 当这些产物被压缩上传到 Linux 服务器后，Linux 下的 Node.js 根本无法在 `node_modules` 中匹配到这种带随机 Hash 名字的包，导致接口直接启动崩溃。

### 1.3 Solution (解决方案)
在 `package.json` 的构建脚本中，显式注入 `--webpack` 标志，**强制 Next.js 16 退回到标准的 Webpack 编译器**进行打包：
```json
"scripts": {
  "build": "prisma generate && next build --webpack"
}
```
*Webpack 编译器会忠实地保留标准的 `require('@prisma/client')` 导入语句，使产物能够在 Linux 的 Node 依赖环境下原生匹配成功。*

## 2. Zod Validation Crash (Next.js 16 废弃配置导致 Zod 校验崩溃)

### 2.1 Symptoms & Logs (现象与日志)
在服务器启动时，项目无法正常拉起，宝塔终端或日志抛出十分诡异且无从定位源码的报错：
```
TypeError: Cannot read properties of undefined (reading 'map')
  at ignore-listed frames
```

### 2.2 Root Cause Analysis (根源剖析)
- 这是由于在 `next.config.js` 的 `experimental` 块中，写了已被 Next.js 16 废弃的旧属性 `serverComponentsExternalPackages`。
- Next.js 16 启动时会使用 Zod 校验 `next.config.js` 的选项，一旦抛出“Unrecognized key(s)”警告，它的报错格式化程序自身有一个逻辑 Bug（试图在 `undefined` 上调用 `.map()` ），进而导致整个项目进程在加载配置的第一秒直接闪退崩溃。

### 2.3 Solution (解决方案)
彻底将废弃的旧属性从 `experimental` 块中移除，改用 Next.js 15/16 原生的根级配置：
```javascript
// next.config.js
const nextConfig = {
  // ... 其它配置
  experimental: {
    cpus: 1,
    workerThreads: false,
    memoryBasedWorkersCount: true,
    // ❌ 绝对禁止在这里写 serverComponentsExternalPackages
  },
  //  正确写法：直接写在根级
  serverExternalPackages: ['@prisma/client', 'prisma'],
}
```

## 3. Loss of Executable Permissions (本地 ZIP 打包上传导致可执行权限丢失 Bug)

### 3.1 Symptoms & Logs (现象与日志)
在宝塔启动项目直接失败，Nginx 反向代理返回 `502 Bad Gateway`。日志报错：
```
sh: 1: next: Permission denied
```

### 3.2 Root Cause Analysis (根源剖析)
- Windows 本地没有 Linux 传统的文件可执行属性（Executable Permission）。
- 无论使用 Python 的 `zipfile` 还是 Node.js 打包，将 `node_modules` 或项目目录压缩为 `.zip` 上传到 Linux 服务器后解压，`.bin/next` 文件都会丢失可执行权限（变成了 644 而不是 755），导致 Node 守护进程无权执行二进制命令，启动即闪退。

### 3.3 Cross-platform Solution (跨平台解决方案)
在 `package.json` 的 `start` 和 `dev` 脚本前置注入一个 Node.js 提权命令：
```json
"scripts": {
  "dev": "node -e \"try { require('child_process').execSync('chmod -R 755 ./node_modules/.bin/') } catch(e) {}\" && next start -p 3000",
  "start": "node -e \"try { require('child_process').execSync('chmod -R 755 ./node_modules/.bin/') } catch(e) {}\" && next start -p 3000"
}
```
* 这种写法的好处在于：**在 Windows 本地开发运行时，即便报错也会被 `try-catch` 完美吞掉不会使构建闪退；而在部署到 Linux 服务器被启动时，能够 100% 自动为软链接加上 755 执行权限，彻底解决权限拒绝问题。*

## 4. Dependency Conflict & Process Deadlock (依赖冲突与进程后台死锁 Bug)

### 4.1 Symptoms & Logs (现象与日志)
在本地终端或后台执行打包脚本时，进度条停滞，日志没有任何输出（控制台假死），或者打包进度极其缓慢甚至直接被网络 EOF 斩断。

### 4.2 Root Cause Analysis (根源剖析)
- 历史 `package.json` 中的 build 脚本中存在类似 `npm install typescript && ...` 的命令。
- 在本地打包时，由于 React 19 / Next 16 的 peer dependencies 存在冲突，运行没有加参数的 `npm install` 会让 npm 陷入长时间的依赖树层层回溯和交互式警告等待（EROLVE），在无人值守的构建脚本后台里表现为进程死锁挂起。

### 4.3 Solution (解决方案)
1. 移除 `build` 脚本里任何包含 `npm install` 的链式行为，保持职责单一。
2. 本地执行包变动时，必须显式附加参数：
   ```bash
   npm install --legacy-peer-deps
   ```

## 5. DLP Non-Privileged Packaging Crash (防泄密非白名单打包密文污染 Bug)

### 5.1 Symptoms & Logs (现象与日志)
- 本地使用 `npm run dev` 测试时界面样式 100% 正常，但通过打包脚本生成 `.zip` 上传至宝塔 Linux 服务器部署后：
  - 线上页面样式大面积崩塌（排版变小、边距失效、自定义高度与配色全丢）。
  - 开发者工具控制台或直接访问 CSS 文件发现头部携带：`%TSD-Header-###%` 字符串与二进制乱码，浏览器将其认定为非法 CSS 语法直接丢弃。

### 5.2 Root Cause Analysis (根源剖析)
- **环境特性**：宿主机安装了企业级透明防泄密系统（DLP/TSD）。
- **进程白名单陷阱**：宿主机内核驱动仅将 `node.exe`、VSCode 等特权进程纳入透明解密范围；而 `python.exe` 或其他未授权脚本工具为非白名单进程。
- **打包污染**：若直接使用 `python pack.py` 或未授权的外部压缩工具打包，Python 读取 `.next/static/css/` 时读取到的是带有密文头的加密字节流，并将其原样打入压缩包。上传至无解密驱动的 Linux 服务器后，导致生产环境所有样式全部变砖。

### 5.3 Solution (解决方案)
- **严禁使用 Python 处理打包**：统一在项目根目录使用专用特权脚本通过 Node.js 内存流读取明文并打包：
  ```bash
  node pack_dlp.js
  ```
- **发布前健康自检**：运行检查脚本验证包内所有 CSS 文件的密文头：
  ```python
  # 确保 is_tsd 恒为 False
  is_tsd = b'%TSD-Header' in css_bytes
  ```

## 6. Static Chunk Disk Cache & Hash Trap (静态资源持久缓存与动态 Build ID 防御机制)

### 6.1 Symptoms & Logs (现象与日志)
- 服务端已确认解压了最新的代码，但用户或开发者在浏览器中刷新（F5）页面后，**页面排版与色彩依然与旧版一模一样**，产生“服务端更新完全没生效”的假象。

### 6.2 Root Cause Analysis (根源剖析)
1. **文件名未更新命中本地硬盘缓存（Disk Cache）**：Next.js 默认构建时，若局部调整未引起整体路由树重构，生成的静态 CSS/JS chunk 文件名哈希可能保持不变（如 `29c00e395ebc4d28.css`）。浏览器及 Cloudflare CDN 依据 URL 强缓存策略，直接从本地 Disk Cache 读取先前已缓存的损坏/旧版文件，根本不会向源站发起真实请求。
2. **纯 CSS 类名受限于加载顺序与网络波动**：关键视觉参数（如封面容器高度、标题字号、黑金高定色）若仅依赖 Tailwind 编译类名，一旦 CSS 文件加载延迟或被缓存阻断，会导致关键样式瞬时降级。

### 6.3 Solution (解决方案)
1. **动态注入唯一 Build ID（击穿全链路缓存）**：
   在 `next.config.js` 中显式配置动态生成 Build ID，使每次构建生成的静态资源带上全局唯一时间戳指纹，强制浏览器和 CDN 废弃全部旧缓存：
   ```javascript
   // next.config.js
   const nextConfig = {
     // ...
     generateBuildId: async () => {
       return 'release-' + Date.now();
     },
   };
   ```
2. **核心业务与高定视觉增加行内 `style` 双保险**：
   对于结果页封面 Header 高度、大标题字号、品牌高定主色调等决定第一视觉印象的核心元素，必须同步注入行内 `style` 属性（如 `style={{ minHeight: '175px', color: '#F6D365' }}`），确保无论网络缓存状态如何，核心排版与色彩 100% 强力生效。
