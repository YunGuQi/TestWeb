# 02_测试设计_6 - 心理测试全链路自检清单 (Pre-Flight SSOT Checklist)

> **定位**：小红书趣味心理测试研发上线的**通用门禁规范与终审验收清单 (SSOT)**。
> 本清单由原【通用 UI 组件自检清单】与【系统安全、精算平衡、心智仿真、防爬脱壳及数据底座风险自检清单】全面合并升级而成。
> 在完成新测试开发或大盘版本迭代后，必须对照本清单逐层核对，不仅要自检全部前端 UI 结构和商业转化交互，还要深度审查题库命题去偏、精算算法、概率健康度、真实心智偏好、全链路防爬脱壳、数据库并发零死锁以及后台配置，确保产品既有极高转化率与视觉冲击力，又具备极高稳定性与资产安全性。

## 🚦 Layer 0: 核心红线门禁速览 (Critical Red Lines)

在进行任何细则审查前，必须首先确认以下 4 项绝对技术红线：
1. **Dependency Freeze (依赖版本冻结)**：核心锁死 `next: 16.2.11`，`tailwindcss: ^3.4.19`（严禁升级到 Tailwind v4，避免大盘样式变量与动画崩塌）。
2. **Schema Freeze (数据库表结构冻结)**：全盘实行“库表复用”策略，严禁修改 `schema.prisma` 或新建实体表，所有测试统一复用 `ActivationCode`、`TestRecord`、`Question`、`Option`、`ResultConfig`、`GlobalConfig`。
3. **Data Hard Isolation (数据硬隔离)**：该测试必须在全局定义独属的英文标识符（`testId`，如 `emotional-friction`、`destiny-lover`、`city-personality`、`family-origin`、`love-species`），贯穿所有数据库配置、API 路由、前端本地缓存命名空间与数字签名负载。
4. **Client Bundle DLP (客户端防脱壳防白嫖)**：所有客户端 React 组件（`'use client'`）绝对禁止 `import` 包含后 70% 深度分析的本地完整数据源文件，编译生成的 `.next/static/` 静态公共 JS 中商业机密词泄露数必须为 0。

## 🧮 Layer 2: 题库命题铁律、精算流水线与心智模型偏好自检清单

*杜绝“千人一面”、“送分送命”与“AI味悬浮”，让算法与内容兼具文学张力与精算平衡。*

### 1. 题库命题四大铁律 (Question Invariants)
- [ ] **平行处事哲学（防社会赞许性坍缩）**：
  - [ ] 全卷题目（标准版 20 题，精简版 15 题）的 4 个选项是否代表 4 种平等、自洽、成熟的人格应对姿态？
  - [ ] 是否彻底消除了“好人 vs 坏人”、“高情商 vs 低情商”、“健康 vs 神经质”的道德送分陷阱？确保不会出现全员一边倒勾选某个完美选项的现象。
- [ ] **双短语律 (Dual-Phrase Cadence)**：
  - [ ] 选项文本是否严格遵守 `【处事动作（4~6字）】 + 【心理动机（6~10字）】` 黄金范式？
  - [ ] 单个选项长度严格锚定在 12~25 字区间，兼具文学网感与真实生活颗粒度？
- [ ] **禁词硬审查（零剧透泄露）**：
  - [ ] 题干与选项中是否 **0 处**出现测试结果画像名称同义词、心理学术语或生造概念（如“内耗”、“觉醒”、“讨好”、“破防”等）？杜绝受众通过词汇猜出算法意图。
- [ ] **等权混维 (Equi-Weighted Shuffling)**：
  - [ ] 全卷各维度出题权重是否绝对均等？单选是否固定 **+1分**（严禁随意出现 +2/+3 不对称加权破坏常模）？
  - [ ] A/B/C/D 选项顺位是否在入库或展示时充分打乱，避免固定顺位偏差？

### 2. 权重算法与常模流水线 (Scoring Pipeline)
- [ ] **Z-Score 相对离差精算**：
  - [ ] 系统是否依据大盘基准均值 $\mu_i$ 与标准差 $\sigma_i$ 计算标准正态离差 $Z_i = \frac{Raw_i - \mu_i}{\sigma_i}$，消除不同题目主观难易度差异？
- [ ] **累积正态分布转换 (normCDF/erf)**：
  - [ ] 是否通过高斯误差函数多项式逼近转换为平滑的常模超越百分位（“超越 XX% 的同龄人”）？
- [ ] **多轴正交去偏与矩阵校准**：
  - [ ] 多轴复合测试（如 `love-species`、`city`）是否引入了消除选项共线性拖累的正交去偏因子（$\alpha$ 消除 A-D / E-H 偏置）或城市偏置校准字典（CITY_BIASES），防止特定属性产生连带失真？
- [ ] **单小数位与动态去重微扰动**：
  - [ ] 前台雷达百分位必须严格保留单小数位（如 `89.4%`），杜绝死板整数；
  - [ ] 是否叠加上下 $\pm 0.4\%$ 的动态伪随机扰动，彻底防御小红书截屏查重机制？

### 3. 概率分布健康度与小红书真实心智偏好仿真
- [ ] **纯随机蒙特卡洛抽样基线 (20,000 次模拟)**：
  - [ ] **无死画像**：所有画像产出概率全员 $\ge 4.0\%$，严禁存在不可触达的长尾死画像；
  - [ ] **无垄断霸榜**：单一画像产出概率全员 $\le 20.0\%$，杜绝千人一面、单画像通吃；
- [ ] **小红书真实用户心智偏好仿真 (20,000 次加权模拟)**：
  - [ ] 注入小红书大盘年轻女性典型心智权重（高敏内耗 35%、大女主独立 25%、讨好顺应 25%、佛系松弛 15%）；
  - [ ] 验证产出是否呈现健康的**双峰转化模型**：
    - **痛点画像（20%~25%）**：如高内耗破防画像，精准激发卡密付费解锁处方；
    - **高光画像（20%~25%）**：如大女主、人间铁壁画像，激发极高社交炫耀与晒单裂变；
    - **长尾画像**：在偏好倾斜下依然平滑分布，无任何画像概率断崖归零。

## 🛡️ Layer 3: 系统安全、代码防脱壳与并发零死锁自检清单

*封死前端抓包与静态反编译白嫖，保障高并发流量下数据库零死锁、零雪崩。*

### 1. 客户端静态代码脱壳防盗 (Client Bundle DLP) —— 【关键防线】
- [ ] **零本地深度数据引入 (No Full Data Import in Client)**：
  - [ ] 检查所有 `'use client'` 客户端 React 组件，**严禁 `import` 本地包含后 70% 深度文案的数据源文件**（如 `data.ts`、`family-origin-data.ts`、`love-species-data.ts`）；
  - [ ] 任何被客户端组件引入的文件，Webpack/Next.js 均会原样打包进浏览器公开可下载的 `.next/static/chunks/` 中；
- [ ] **轻量元数据物理分离**：
  - [ ] 客户端若需渲染物种图鉴或双人合盘，必须建立专用的轻量客户端文件（如 `love-species-client.ts`），仅包含名称、emoji、标签等公开属性，物理剔除所有破防名场面与处方解析；
- [ ] **静态 Chunk 物理反编译扫描**：
  - [ ] 运行 `npm run build` 后，通过脚本反编译扫描 `.next/static/` 目录下的所有 JS 文件，确认核心商业机密关键词（如深度分析段落词）**0 命中泄露**。

### 2. 服务端真脱敏与全链路安全防护 (Server-Side DLP & Security)
- [ ] **交卷物理剔除 (Physical Data Stripping)**：
  - [ ] `/api/submit` 接口在向前端返回结果前，是否调用了真脱敏函数（如 `stripPremiumContent`），**在内存中通过 `delete` 物理剔除**后 70% 的所有深度分析字段？彻底封死通过 F12 删除模糊蒙层 DOM 节点的白嫖漏洞；
- [ ] **核销动态履约 (Dynamic Fulfillment)**：
  - [ ] 后 70% 深度分析必须严格由 `/api/verify` 接口在完成卡密核销与设备绑定后，从服务端动态组装返回；
- [ ] **安全防护三件套**：
  - [ ] **防重放签名**：前端请求是否携带私钥计算的 `x-sign` 与 `x-timestamp`，时间戳有效窗口严格限制在 120 秒内；
  - [ ] **防爬虫会话门禁**：进入答题前是否通过 `/api/init-test` 建立了强力 HttpOnly Session Cookie，拦截脚本裸刷；
  - [ ] **精准频控**：提交接口（单 IP 每分钟最多 10 次）、核销接口（单 IP 每分钟最多 6 次）是否配置全局 Rate Limit，超限返回 429 阻断。

### 3. 数据库高并发与零死锁架构 (Database Concurrency & Zero Deadlock)
- [ ] **原子化核销事务 (Single-Row Atomic Transaction)**：
  - [ ] 卡密核销是否在 `prisma.$transaction` 内完成？
  - [ ] 查询与更新是否严格基于唯一复合索引（`[code, testId]`）单条锁定，绝对不引入跨表外键级联锁或长耗时网络请求，**从设计原理上实现 0 数据库死锁**；
- [ ] **设备绑定幂等放行**：
  - [ ] 是否支持 `maxUses` 设备上限判定，并在同一设备重复访问时基于幂等机制直接放行，不消耗使用次数；
- [ ] **非阻塞异步流水写入与降级**：
  - [ ] `TestRecord.create` 及大盘统计写操作是否被包裹在 `try...catch` 块中？突发流量下即便记录写入轻微延迟或降级，也绝不阻断 C 端用户的正常出票流转；
- [ ] **多平台本地缓存硬隔离**：
  - [ ] 浏览器 `localStorage` 缓存键（如 `verified_family-origin`、`verified_emo`、`deviceId`）是否全局强制携带 `testId` 命名空间前缀，彻底杜绝不同测试并存时的缓存污染与权限串扰。
